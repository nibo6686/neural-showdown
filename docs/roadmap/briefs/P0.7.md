> **Slice P0.7 — evaluation harness (the capability scoreboard).**
> Repo: `C:\Users\cloud\Downloads\neural\final`, branch `main-native11`
> (after P0.5c3). Read `AGENTS.md` and `docs/roadmap/LONG-TERM-PLAN.md` §2
> first. In particular: no delegation, no full suites, no known timeouts.
>
> **Goal.** A reproducible way to measure playing strength, available before
> any model work. Every later model, search or feature change reports its
> numbers here. This is the plan's second scoreboard, beside the coverage
> registry.
>
> ### What to build
> 1. **Agent interface** (`sim-core/src/bench/agent.ts`):
>    `choose(request, view, rng) → canonical action`. It uses only the
>    agent's own perspective view and request (no hidden state), and returns
>    only canonical legal actions. Adapt the existing baselines:
>    - `random`: the seeded `RandomBaselineAgent`;
>    - `heuristic`: `HeuristicBaselineAgent`;
>    - **new `greedy`**: picks the legal move with the highest expected damage
>      against the opponent's active Pokémon, using `damage_calc.ts` and
>      public information only. It doesn't Terastallize and switches only
>      when forced. This is the standard "damage calculator" baseline.
>
>    Keep the interface generic, so a Python or model agent can plug in later
>    through a subprocess. Don't build that adapter now.
> 2. **Runner** (`tools/bench/index.cjs` or a TS entry built into `dist`).
>    Use a lean environment, not the authoritative pipeline: battles are
>    played through `LocalBattleEnv` with external controllers on both sides,
>    without capture, publication or knowledge authority. Speed matters here.
>    - **Paired design:** for each seed, play the battle twice with the agents
>      swapping sides. The same seed generates the same two teams, so each
>      agent plays both teams.
>    - Seeds come from a fixed, committed list (`tools/bench/seeds.json`), so
>      the same command produces identical results.
>    - Record per game: seed, side, winner (or tie), turns, illegal or
>      rejected choices (must be 0; nonzero fails the run), errors, and wall
>      time.
> 3. **Report.** For each matchup (round robin over `random`, `greedy` and
>    `heuristic`): wins, losses and ties; win rate with a **Wilson 95% CI**;
>    mean turns; games per second. Write it to `docs/roadmap/benchmarks.md`
>    (a table, plus the exact command, engine commit and seed-list hash) and
>    to a machine-readable `tools/bench/results/<date>.json`. Results are
>    small; commit them.
> 4. **Determinism test** (`sim-core/tests/bench.test.ts`, in `test:fast`):
>    - 3 seeds × 2 sides for random vs heuristic give byte-identical result
>      records on two runs;
>    - an agent that returns an illegal action is caught and fails the run;
>    - an agent that reads the opponent's private request can't: the interface
>      never receives it.
>
> ### Sizes and time
> - Time 50 pairs first. Then choose N so a full round robin finishes in about
>   an hour on this machine. Target N = 500 pairs (1,000 games) per matchup;
>   that gives roughly ±3 points near 50%. If it's too slow, report the measured
>   throughput and use the largest N that fits. Run the long benchmark in the
>   background and report its time. It isn't part of `test:fast`.
> - Cap each battle at the engine's own turn limit. If a battle exceeds
>   1,000 turns, record it as a tie with a flag; that should be rare.
>
> **Out of scope.** Old Python checkpoints as a control (they need the legacy
> feature pipeline; list it as a follow-up with an estimate); model agents;
> search; full suites.
