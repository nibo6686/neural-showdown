# Prompt55 — owner-addressed decision adoption design

Recommend an **experimental opt-in local TS ordering consumer**, not model or training adoption. The real caller is candidate `sim-core/src/pipeline_episode.ts`: `runPipelineEpisode`/`continuePipelineEpisode` → `executeEpisode` → `actingPlayers` → `actionTuples` → synchronous `action_order(observation)` → `canonicalActionFromLegalAction` → `session.step/stepForcedSwitch/stepRevival`. No production caller currently reads `readOwnerKnowledge`; accepted tests prove private access, not downstream adoption. `scripts/simulator-record-comparison.cjs` calls the episode runner, but its default comparison/publication path must remain unchanged. Python tournament/selfplay policies use separate RPC/features and are excluded.

Future write boundary: narrow `pipeline_episode.ts` opt-in dispatch, `pipeline_integration.ts` owner-frame issuance/recheck, and new `owned_decision_input.ts` private controller/types plus focused test. No knowledge profiles, B1/B2, canonical-action algorithms, wire/result schemas, extractors, models or scripts need changes. Use accepted Prompt48/50/53/54 facts; do not add another field profile.

## Proposed internal API and exact joins

A trusted local coordinator registers distinct recipient objects through existing `knowledge_recipients`, retains them, and supplies separate per-owner synchronous callbacks under new TS-only `owned_action_order` registrations. Reject coexistence with legacy `action_order`; require explicit versioned `policy_id` and an `accept_incomplete:true` opt-in. Continuation must possess the original registered recipients; owner labels, copied tokens or a fresh registration cannot recover authority. Do not export a public owner-string capability factory.

Propose `session.withOwnedDecisionInput(recipient, callback): OwnedDecisionOrder`, an opaque held order exposing readonly indices only. Internally issue a frozen `OwnedDecisionInput` containing only the addressed legitimate observation, inseparable `OwnerKnowledgeRead` projection/binding pair, immutable `CanonicalActionRequestContext`, legal indices, and literal `completeness:'incomplete'`. Expose no session, recipient token, environment, ledger/history, native actor, source or proof capability. A private frame table retains the actual recipient, current knowledge handle/read, issuer/session occurrence, environment, committed boundary, latest ledger boundary/current delivery/selected receipt and an immutable action-context snapshot. A frame value or structural validator alone grants no authority.

Issuance checks the authentic current handle/read and owner; exact committed boundary/issuer and latest delivery row; pair observation_id/prefix_cursor against the addressed observation/cursor; descriptor sequence/cursor against that row; and a fresh owned request read from this environment. `ManagedPlayer.getRequest()` clones its held request; `LocalBattleEnv.getRequest()` returns that clone. Exact latest ledger boundary/current delivery/selected receipt membership supplies request authority. Compare the observable request and fresh read’s complete canonical-action contexts solely as freshness/action corroboration within this chain. Never equate clone identity, rqid, request equality, hashes, names or timestamps with authority. Retain selected receipt/delivery references privately even when equal bytes recur.

After callback, repeat these joins and ensure unchanged authenticated delivery membership and matching fresh request context before accepting its full, unique permutation of current legal indices. Then construct/serialize canonical actions against the freshly corroborated request context. `session.assertOwnedDecisionBatch(orders)` resolves authentic order-object membership to the private frames; copied orders cannot substitute. After both callbacks, recheck **both** frames immediately before the existing transition call, with no await between validation and submission. Direct canonical APIs remain compatible; they gain no new knowledge authority. An old canonical action alone cannot substitute for an owned-decision frame.

## Meaning and lifecycle

Inputs expose immutable original roster/species/ability/item/moves, current owned HP/status/faint/item/ability IDs, and ordinary emitted request-option PP/maxPP. Zero PP is known; disabled options are not permission. Empty item is affirmative absence; empty/omitted ability is blocking unknown. Current IDs say nothing about effectiveness/suppression/base ability or item cause/history. Request options say nothing about possession/incarnations. Public-current/unimplemented adapters, bench PP, transformed/locked alternatives, recovery/updated-overlay lineage and completeness remain blocked. Do not fill missing facts from originals, species priors, raw native state or legacy observation features. Legitimate public/owned observation remains separately labeled existing input, not adopted K authority.

Creation issues frames only after successful joint installation. Each acting owner’s descriptor must match its request kind: ordinary_pp for moves, forced_switch or revival_selection for those selections. Joint decisions invoke each owner separately. One-sided forced/Revival selection invokes only the acting owner through the existing action kind/validator; waiting owner gets no decision callback. Terminal/requestless gets none. Unsupported request-source/descriptor or failed joins stop opt-in selection rather than fall back; aggregate incompleteness and accepted unknown individual facts remain permitted. The policy explicitly handles unknown facts; it may order canonical legal indices without using unknown properties, but cannot certify complete inputs.

Callback exceptions, promises, malformed permutations and invalid actions fail before writes with fixed diagnostics that omit private inputs/error payloads. No silent fallback or recoverable partial choice. Rejected transition retains committed holdings/pair: discard attempted decision frames and reissue fresh frames from the unchanged boundary for any existing bounded retry. Successful transition invalidates old frames synchronously with installation; close revokes before cleanup. Earlier inert values remain history. The runner owns the session exclusively; callbacks receive no mutation API. A synchronous selection guard rejects reentrant transition/decision calls before candidate creation; close instead revokes immediately and makes the pending batch fail. Separate registrations limit supplied data; in-process callbacks are trusted code, not a sandbox against deliberate shared-memory exfiltration.

## Approval decisions and focused future checks

Approve the opt-in TS callback/API and explicit incomplete-input policy; default APIs, ordering, output bytes, publication and fidelity=false stay unchanged. Reject serialized/Python/RPC adoption pending a separate persisted authority/profile contract. No current adoption is claimed by this design.

Future exact short checks: both-owner real runner callbacks; changed Trace/current ability or consumed item influences actual ordering while originals remain identical; forced/Revival actor-only invocation and wait/terminal exclusion; exact boundary/request/delivery joins including equal-byte fresh occurrences; copied/stale/foreign/wrong-owner denial; unsupported source and nullable PP handling; first/second callback failure, invalid action and rejected candidate retain committed state with fresh retry; close revocation; privacy and default literal parity. No long episodes or models. Complete/training-ready inputs require separately accepted missing adapters, completeness/fidelity and training gates.

## Independent review

The design now uses exact private committed ledger membership as authority and fresh context comparison only as corroboration; no env_manager authority seam is added. It also explicitly separates unsupported request-source stops from allowed incomplete/unknown facts. Opaque held orders, joint batch recheck and reentrant selection guard were reviewed. Final disposition: **ACCEPT** after these amendments; no remaining material static design concern. Read-only source inspection and document editing only; no tests, builds, imports, battles, source changes or runtime validation performed.
